# The Self-Improvement Loop

**Where Can We Use Karpathy's `autoresearch` Pattern in Content Hub V2?**

**Type:** Opportunity survey (no implementation, no timing commitment)
**Date:** 2026-05-28
**Related:** [[Local_First_Skill_Engine_Plan]], [[Refined_Pipeline]], [[Researcher_Optimisation]]

---

## 1. Context — Why This Matters

Karpathy released a tiny open-source framework called `autoresearch`. The idea is dead simple:

> Let an AI agent **change one file**, **run a test**, **score the result**, then **keep the change or throw it away** — and repeat that loop overnight without you babysitting it.

He built it for ML training runs. But the **pattern itself** — *modify → score → keep-or-revert → repeat* — works anywhere you can measure quality.

Content Hub V2 has 10 prompts that were written once and never tested systematically. Every video script, hook, and title is generated by prompts nobody has measured. That's a huge improvement opportunity hiding in plain sight.

This document is a **survey** of 5 places autoresearch fits your system, with effort/value ratings, an honest "fact vs. assumption" split for each, and concrete file-by-file mapping.

---

## 2. How autoresearch Works (in 30 seconds, layman terms)

Imagine you have a recipe and a way to score the cake it produces (1-10 from a taste tester). autoresearch is the kitchen robot that:

1. Tweaks one ingredient in the recipe.
2. Bakes the cake (fixed time, fixed oven settings — same every run).
3. Scores it.
4. If the score went up, **keeps the tweak.** If it went down, **rips it out.**
5. Tweaks something else. Repeats all night.

In Karpathy's repo:
- **The recipe** = `train.py` (the only file the agent can touch)
- **The oven** = `prepare.py` (fixed — agent cannot change)
- **The taste tester** = a number called `val_bpb`
- **The rulebook** = `program.md` (you write this before bedtime: "tonight, optimize for X")

**Three things make the pattern work:** one mutable file, one fixed metric, one rulebook.

### 3.1 Karpathy's `train.py`  →  our `prompts/<skill>.md`

**Karpathy's version:** PyTorch model + optimizer + training loop. The only file the agent is allowed to mutate.

**Our version:** the prompt markdown file. The only file `/prompt-lab` is allowed to mutate.

**Applies to all 8 skills:** [[researcher]], [[ideation]], [[hook]], [[outline]], [[title]], [[cascade]], [[short-form]], [[voice-cleanup]].

**Status:** all 8 files already exist on disk in `prompts/`.

**What's inside `prompts/hook.md` today (excerpt):**
> *"Generate 5 Kallaway hook variations using the 3-stage structure: scroll stop, curiosity gap, payoff promise. For each hook, produce a Spoken Line, a Visual Anchor, and a Curiosity Gap Marker..."*

**What `/prompt-lab` does to it each iteration:** rewrites sections, deletes lines, adds rules, restructures examples. Every variant gets a git commit. Bad variants → reverted. Good variants → kept and built on.

### 3.3 Karpathy's `val_bpb` metric  →  our `prompt-lab/scorers/<skill>_scorer.py`

**Karpathy's version:** validation bits-per-byte — a single floating-point number. Lower is better.

**Our version:** Python function that ingests skill output, returns **one floating-point number**. Higher is better.

**Applies to all 8 skills.** Each gets its own scorer file with a skill-specific formula:

| Scorer file (new) | Formula |
|---|---|
| `hook_scorer.py` | LLM-judge avg(scroll_stop, curiosity_gap, payoff) across 5 hooks |
| `outline_scorer.py` | programmatic (6 stages present, durations sum) + LLM-judge talking-point specificity |
| `title_scorer.py` | head-to-head LLM-judge win-rate vs. `skills/data/competitor_titles.json` |
| `voice_cleanup_scorer.py` | **programmatic**: `−banned_phrase_count + 0.5 × LLM-judge(voice_fidelity)`. Most trustworthy scorer — banned-phrase count is an exact integer. |
| `researcher_scorer.py` | LLM-judge: brief contains primary sources? gap analysis present? |
| `ideation_scorer.py` | LLM-judge: 9 distinct ideas? gap reasoning per idea? audience desire mapped? |
| `cascade_scorer.py` | LLM-judge per artifact (blog, twitter, linkedin) — composite |
| `short_form_scorer.py` | LLM-judge: 3 length variants present? hook-payoff intact at 30s/60s/90s? |

**Pseudocode of `hook_scorer.py`:**
```python
def score_hook_output(generated_hooks: list[str]) -> float:
    scores = []
    for hook in generated_hooks:
        judge = llm_judge(
            hook=hook,
            rubric="Score 0-10 on each axis: scroll_stop, curiosity_gap, payoff_promise"
        )
        scores.append(mean([judge.scroll_stop, judge.curiosity_gap, judge.payoff]))
    return mean(scores)  # average across all 5 hooks
```

**Status:** 8 scorer files new.

> The path `Content-Hub-Vault-V2/00-Management-V2/brief.md` is the **proposed location** where this file *would* live. It gets **created when Opportunity 3 is built**. You'd write it once, then overwrite it each night before kicking off a new `/prompt-lab` run.

## 5. The 5 Opportunities

### Opportunity 1 — `/prompt-lab` (Autonomous Prompt Optimizer) — HIGHEST VALUE

**The pitch:** Point it at any prompt in `prompts/`, go to sleep, wake up to a measurably better prompt.

**Facts:**
- All 10 prompts already exist as plain `.md` files — the "mutable file" is already there.
- Each skill is already callable from Python (`skills/*.py`), so the loop can run them headlessly.
- Per-skill evals already exist (`.claude/skills/<skill>/iteration-1/`) — scoring scaffolding is partially there.

**Assumptions:**
- An LLM-judge scoring rubric can produce stable, comparable scores across runs. *(Plausible — standard practice — but needs validation. A wobbly judge ruins the whole loop.)*
- Optimizing one prompt won't break the next stage downstream. *(Risk — mitigated by the final integration pass in §7.)*

**Effort:** Medium. Reuses existing per-skill eval harness.
**Value:** **Highest.** Every downstream output gets better. Pays off forever.

---

### Opportunity 2 — `pipeline_results.tsv` (Lightweight Tracking Layer)

**The pitch:** A single spreadsheet-style file that records every pipeline run so you can compare them.

**Facts:**
- No such file exists today (confirmed).
- `pipeline.py` already has natural hook points where logging could be added.
- Direct port of autoresearch's `results.tsv`.

**Assumptions:**
- A simple TSV is enough; no SQLite/Postgres needed yet. *(Probably true at current scale.)*

**Effort:** Low. ~50 lines added to `pipeline.py` + a TSV file.
**Value:** Medium alone — high as a prerequisite. **Opportunity 1 needs this** to track variant scores.

---

### Opportunity 3 — `brief.md` (Per-Run Instruction File)

**The pitch:** Write a one-page brief before bed; the whole pipeline reads it and shapes every decision around it.

**Facts:**
- No per-run instruction file exists today.
- Direct port of autoresearch's `program.md`.

**Assumptions:**
- You actually want to write a brief before each run. *(Worth confirming — if you prefer CLI flags, this is just extra ceremony.)*
- Skills can be modified to read it without major refactor. *(Likely — most skills already accept a research-brief file path.)*

**Effort:** Low-medium. New file convention + small read in each of 8 skills.
**Value:** Medium. Biggest payoff combined with Opportunity 5.

---

### Opportunity 4 — Formalize Fixed Budgets as Logged "Experiment Parameters"

**The pitch:** You already have hard limits (9 ideas, 5 hooks). Log them so you can see which limits worked.

**Facts:**
- Skills already enforce hard counts (confirmed: ideation = 9, hook = 5, short_form = 3 lengths).
- Researcher has a query budget already partially enforced.

**Assumptions:**
- These numbers are worth experimenting with at all. *(Maybe not — Kallaway-trained numbers may be locked-in by the methodology.)*

**Effort:** Trivial. A few extra columns in the TSV from Opportunity 2.
**Value:** Low until you tweak the numbers. Cheap insurance.

---

### Opportunity 5 — `/pipeline-loop` (Overnight Autonomous Content Run)

**The pitch:** Extend `/run-pipeline` with a quality gate — if a stage scores below threshold, retry with a different angle, automatically.

**Facts:**
- `/run-pipeline` already exists and runs the full chain autonomously.
- It does NOT currently have a quality gate or retry loop.

**Assumptions:**
- Stage-level quality scoring is reliable enough to drive retry decisions. *(Same risk as Opp 1.)*
- "Retry with different angle" can be implemented without prompt babysitting. *(Unclear — needs a controlled experiment.)*

**Effort:** High. Depends on Opps 1, 2, 3 being solid first.
**Value:** Very high if it works. Most fragile of the five.

## 6. Recommended Build Order

1. **Opportunity 2** (`pipeline_results.tsv`) — cheap, unlocks everything else.
2. **Opportunity 1** (`/prompt-lab`) — highest standalone ROI.
3. **Opportunity 3** (`brief.md`) — small lift, opens door to Opp 5.
4. **Opportunity 4** (logged budgets) — falls out of Opp 2 for free.
5. **Opportunity 5** (`/pipeline-loop`) — only after 1-4 prove the scoring layer is trustworthy.

## 7. Run Architecture — Locked Decision

**Per-prompt, one at a time, in pipeline order. Then ONE final integration pass.**

This matches Karpathy's own approach (he optimizes `train.py` with `prepare.py` frozen — never tries to optimize the whole stack at once).

**The 9-night schedule:**

| Night | Target prompt |
|---|---|
| 1 | `prompts/researcher.md` |
| 2 | `prompts/ideation.md` |
| 3 | `prompts/hook.md` |
| 4 | `prompts/outline.md` |
| 5 | `prompts/title.md` |
| 6 | `prompts/cascade.md` |
| 7 | `prompts/short_form.md` |
| 8 | `prompts/voice_cleanup.md` |
| 9 | Full-pipeline integration pass — revert any per-prompt change that broke the chain |

Each night: ~5 min per iteration × ~8 hours = ~96 prompt variants tested. Winner committed to git, losers reverted.

**Why per-prompt wins:**
- Fast loop (~5 min vs. 30+ min for end-to-end).
- Easy to debug — you know exactly which prompt change caused which score delta.
- Cheap to revert — if Night 3's hook prompt is worse, roll back that one file.

**One-command convenience:** `/prompt-lab --all` could orchestrate all 9 nights automatically while keeping the per-prompt architecture underneath. UX wrapper, same architecture.

## 8. What You'll Notice After All 5 Are Built

Stage-by-stage, with the **exact scoring metric** for each and which **Opportunities** drive each gain. Honest answer: real improvement, but not magic.

| Stage | Today | After all 5 | Scoring metric (the actual number) | Opportunities involved | Realistic gain |
|---|---|---|---|---|---|
| **Hooks** | First-draft prompt — sometimes punchy, sometimes mid | Hook prompt tuned against Kallaway rubric. Duds drop out. | **Kallaway 3-axis LLM-judge (0-10 each):** scroll-stop, curiosity-gap, payoff promise. Composite = avg. | Opp 1, Opp 2 | 10-30% more hooks pass the scroll-stop bar |
| **Outlines** | Dopamine Ladder followed; pacing varies | Consistently hits all 6 stages with tighter talking points | **Mix: programmatic + LLM-judge.** Programmatic: all 6 stages? durations sum? Talking-point count in range? LLM-judge: specificity 0-10. | Opp 1, Opp 2, Opp 4 | ~20% less padding |
| **Titles** | 10 candidates, hit rate varies | Title prompt rewards titles that beat competitor benchmarks | **Head-to-head LLM-judge vs. `skills/data/competitor_titles.json`.** Score = win-rate %. | Opp 1, Opp 2 | More usable winners per batch |
| **Voice cleanup** | Removes banned phrases; still reads AI-ish | AI-ism count near-zero, tone markers preserved | (a) **Banned-phrase count from `prompts/voice_cleanup.md` list — exact integer, programmatic, the most trustworthy metric in the system.** (b) LLM-judge: voice fidelity 0-10. | Opp 1, Opp 2 | Noticeably less robotic |
| **Cross-pipeline** | One dud stage = manual re-run | Quality gate auto-retries duds with different angle | **Per-stage threshold** (each ≥ 7/10) + **final integration LLM-judge** 0-10. Below threshold → retry stage. | Opp 2, Opp 3, Opp 5 | Way less hand-holding |

**All 5 Opportunities are covered by this table** — viewed from the outcome side:
- **Opp 1** drives 4 of 5 rows (hook, outline, title, voice).
- **Opp 2** is invisible but required by every row.
- **Opp 3** powers the cross-pipeline retry steering.
- **Opp 4** shows up in the outlines row (logged stage budgets).
- **Opp 5** = the cross-pipeline row entirely.

**Compounded effect:** A 15% better hook + 15% better outline + 15% better voice ≠ 45%, but the final video feels meaningfully sharper than today's first-draft pipeline.

**The honest ceiling:** Quality lift is **capped by the scorer**. If your LLM-judge gives noisy scores, you'll plateau fast — maybe 10% instead of 30%. The only way past that is feeding **real audience signal** (view-through rate, retention, CTR) into the loop. That's a v2 of the v2.

**What you will NOT get:** 2x quality, viral guarantees, or a system that removes your judgment. You're still the final taste tester. The robot just stops handing you obvious duds.

## 9. What I'm NOT Recommending

- **Don't port the ML training code.** autoresearch's `torch`/GPU/`train.py` parts are irrelevant — you're not training models.
- **Don't build the scorer last.** The whole pattern lives or dies on whether the score is trustworthy. Noisy scorer = theater.
- **Don't start with Opportunity 5.** Most fragile. Earn it after 1-4.
